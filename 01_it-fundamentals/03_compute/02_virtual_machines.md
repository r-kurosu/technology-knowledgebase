# 仮想マシン

## 1. 概念理解

### 学ぶ範囲

VM、イメージ、インスタンス、OS管理、起動と停止、永続ディスク、配置。

### イメージとインスタンス

[01_process_memory_and_virtualization.md](01_process_memory_and_virtualization.md)の「プログラム vs プロセス」と同じ構造で対応づけられる。

| | プロセス（前回） | VM（今回） |
|---|---|---|
| 静的な雛形 | プログラム | イメージ（AMI） |
| 実際に動いている実体 | プロセス | インスタンス |

- イメージに入っているのはOS・インストール済みソフトウェア・設定などの**ディスクの雛形**
- スペック（vCPU数・メモリ量）を決めるのはイメージとは別レイヤー（インスタンスタイプ）の役割
- 同じイメージ（プログラム）から複数のインスタンス（プロセス）を起動できる点も共通
- インスタンスは物理マシンそのものではなく、ハイパーバイザー上で動く**仮想的な実体**（前回の「物理マシン vs 仮想マシン」の整理と一致）

### OS管理と責任共有モデル（Shared Responsibility Model）

前回の構成図（ハイパーバイザー → VM → OS/カーネル）で、OS/カーネルの層は誰が用意し管理するかを考えると境界線が見える。

| 層 | 管理者 |
|---|---|
| 物理ハードウェア・ハイパーバイザー（クラウドそのものの安全性） | AWS |
| ゲストOS・ミドルウェア・アプリ・データ（クラウドの中身） | ユーザー |

- EC2はこの境界が「ハイパーバイザーの直上」にある → OSの選択も、パッチ適用・アップデートもユーザー責任
- ECS（特にFargate）が楽なのは、この境界線がAWS側にずれてOSを選ぶ概念自体がなくなるため（EC2起動タイプのECSは裏のEC2インスタンスのOSパッチは結局ユーザー責任のまま）
- **VMの自由度と運用負荷はセット**：OSを自由に選べる代わりに、パッチ適用などの運用もセットでついてくる
