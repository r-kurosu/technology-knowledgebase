# 仮想マシン

## 1. 概念理解

### 学ぶ範囲

VM、イメージ、インスタンス、OS管理、起動と停止、永続ディスク、配置。

### イメージとインスタンス

[01_process_memory_and_virtualization.md](01_process_memory_and_virtualization.md)の「プログラム vs プロセス」と同じ構造で対応づけられる。

| | プロセス（前回） | VM（今回） |
|---|---|---|
| 静的な雛形 | プログラム | イメージ（AMI） |
| 実際に動いている実体 | プロセス | インスタンス |

- イメージに入っているのはOS・インストール済みソフトウェア・設定などの**ディスクの雛形**
- スペック（vCPU数・メモリ量）を決めるのはイメージとは別レイヤー（インスタンスタイプ）の役割
- 同じイメージ（プログラム）から複数のインスタンス（プロセス）を起動できる点も共通
- インスタンスは物理マシンそのものではなく、ハイパーバイザー上で動く**仮想的な実体**（前回の「物理マシン vs 仮想マシン」の整理と一致）

### OS管理と責任共有モデル（Shared Responsibility Model）

前回の構成図（ハイパーバイザー → VM → OS/カーネル）で、OS/カーネルの層は誰が用意し管理するかを考えると境界線が見える。

| 層 | 管理者 |
|---|---|
| 物理ハードウェア・ハイパーバイザー（クラウドそのものの安全性） | AWS |
| ゲストOS・ミドルウェア・アプリ・データ（クラウドの中身） | ユーザー |

- EC2はこの境界が「ハイパーバイザーの直上」にある → OSの選択も、パッチ適用・アップデートもユーザー責任
- ECS（特にFargate）が楽なのは、この境界線がAWS側にずれてOSを選ぶ概念自体がなくなるため（EC2起動タイプのECSは裏のEC2インスタンスのOSパッチは結局ユーザー責任のまま）
- **VMの自由度と運用負荷はセット**：OSを自由に選べる代わりに、パッチ適用などの運用もセットでついてくる

### 起動と停止（Stop / Terminate）

| | Stop | Terminate |
|---|---|---|
| コンピュート（インスタンス時間）課金 | 止まる | 止まる |
| EBSストレージ課金 | 継続する | デフォルトではボリュームごと削除される（"Delete on Termination"設定次第で残せる） |
| 再開 | Startで再開可能、データはEBS上に残る | 不可（インスタンスは完全に消滅） |

### 永続ディスク（インスタンスストア vs EBS）

| | インスタンスストア | EBS |
|---|---|---|
| 物理的な位置 | ホストマシンに直接ローカル接続 | ネットワーク越しの独立したストレージサービス |
| 速度 | 速い（ローカルディスク） | ネットワーク越しなので相対的にオーバーヘッドがある |
| 永続性 | Stop・Terminate・ホスト障害で消える（揮発性） | インスタンスと切り離されて存在。Terminateしても"Delete on Termination"がfalseなら残る |
| 付け替え | 不可（そのホストに固定） | 可能（デタッチして別インスタンスにアタッチし直せる） |
| 用途 | キャッシュ・一時データ・スクラッチ領域 | OS本体・DBデータなど残したいデータ |

本質は「揮発性の程度」ではなく、**EBSがインスタンスとは別のライフサイクルを持つ独立したサービス**であること（付け替えできるのもそれが理由）。

### 配置（AZ分散・Placement Group）

- 複数AZへの分散配置の目的：**可用性向上**。各AZは物理的に独立したデータセンター群（電源・ネットワークも別系統）なので、1つのAZの障害が他に波及しない
- **Placement Group**でAZ内の配置をさらに制御できる
  - **Cluster**：低レイテンシ通信のため物理的に近くに集める（HPCなど）
  - **Spread**：異なるハードウェアに分散し、同時障害のリスクを下げる
  - **Partition**：大規模分散システム（Hadoop、Cassandraなど）向けに、パーティション単位で障害ドメインを分ける
